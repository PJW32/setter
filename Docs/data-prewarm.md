# 데이터 사전 수집 운영

사용자의 첫 추천 요청 전에 지역·실거래·시설·목적지역별 통근 데이터를 준비한다. `scripts/prewarm_data.py`는 웹 백엔드와 같은 `DataService`를 사용하며 SQLite와 응답 캐시를 재사용한다. Gemini와 ODsay는 호출하지 않는다. 추천 점수·프롬프트·검색 반경은 변경하지 않는다.

## 권장 실행 국토부 실거래만 준비

```bash
# 기존 수집 지역의 국토부 응답 캐시만 사용. 외부 호출 0회
python scripts/prewarm_rent.py --saved-regions --offline

# 지정 시군구만 준비 (성남 분당구). --offline 없으면 누락 자료는 국토부 API 호출
python scripts/prewarm_rent.py 41135 --offline
```

`data/rent_snapshot.sqlite`에 국토부 원본 응답을 기존 `molit.normalize`로 정규화해 보관한다. 카카오・Gemini・ODsay는 호출하지 않는다. 원본 캐시는 덮어쓰지 않는다. 지역 코드・주택 유형・계약월・정규화 버전별 완료와 출처・구축 시각(UTC)을 저장한다. 전체 페이지 확보・정규화에 성공한 묶음만 트랜잭션으로 완료 처리하며 실패 묶음은 재실행 시 재시도한다. 0건인 정상 응답도 완료로 기록한다.

기존 지역 수집기는 이 스냅샷에서 기간과 버전이 일치하는 완료 묶음을 먼저 읽는다. 행 수・지역・월을 검증하고, 없거나 손상된 묶음은 기존 국토부 API 흐름으로 대체한다. 기존 `store.sqlite`의 완료 지역을 자동 갱신하지는 않는다. 새 스냅샷은 배포 전 점검할 준비 자료이며, 서버로 자동 전송되지 않는다.

로컬 검증 기록: 2026-11-22, 기존 국토부 캐시 480개를 읽어 13개 시군구 × 3유형 × 12개월 = 468묶음, 138,831건 구축. 네트워크 호출 없이 완료했다. 전체 지역・시설・통근이 새로 준비됐다는 의미는 아니다.

## 전체 수집 명령의 사용 범위

카카오 로컬・경로 응답의 장기 DB 저장 및 가공 결과 재사용은 별도 허용 범위를 확인해야 한다. 기존 `store.sqlite`와 파일 캐시에는 카카오 기반 자료가 있으므로, 이를 그대로 공개 배포용 스냅샷으로 내보내지 않는다. 이 변경에서는 기존 자료를 임의로 삭제하지 않고 카카오 결과 사전 수집도 실행하지 않았다.

공식 안내: [로컬 API 저장・캐시 범위](https://devtalk.kakao.com/t/api/140197), [경로 결과 저장・재사용 범위](https://devtalk.kakao.com/t/api/151736).

전체 수집 명령은 기본 차단되며, 실제 사용 범위가 별도로 확인된 경우에만 `--include-kakao`를 지정한다. 이 옵션 자체가 공급자의 허가를 대신하지 않는다.

## 전체 수집 실행

저장소 루트와 Python 가상환경에서 실행한다. 데이터 준비는 서버를 띄우지 않아도 가능하다. 사전 수집 중 같은 지역에 대한 웹 요청을 함께 실행하기보다는 수집을 끝낸 뒤 시연한다.

```bash
# 외부 호출 없이 저장된 지역과 목적지역별 통근 행 수 확인
python scripts/prewarm_data.py --status

# 먼저 판교역 데이터 준비 또는 재사용 확인
python scripts/prewarm_data.py 판교역 --include-kakao

# 다음 필요한 목적지만 추가
python scripts/prewarm_data.py 강남역 여의도역 --include-kakao

# settings.PREWARM_DESTINATIONS 전체를 순서대로 준비
python scripts/prewarm_data.py --all --include-kakao
```

인수 없이 실행하면 도움말과 설정된 목적지만 출력하고 수집하지 않는다. `--status`, `--all`, 목적지 직접 지정은 서로 함께 사용할 수 없다. 실제 수집에는 `KAKAO_REST_API_KEY`와 `DATA_GO_KR_SERVICE_KEY`가 필요하다. 어느 하나라도 없으면 DB 초기화·수집 전에 종료하여 실거래 없이 지역을 수집 완료로 저장하는 상황을 피한다.

## 저장과 재사용

- 지역·거래·시설: 기존 `data/store.sqlite`에 저장한다. 완료된 시군구는 기존 수집기의 규칙대로 건너뛴다.
- 통근: 같은 DB의 `(dong_code, dest_key)` 값이 있으면 사용하고 없는 조합만 조회한다.
- 응답: `data/cache/`를 재사용한다. 목적지 이름 검색과 후보 시군구 탐색은 여전히 실행하지만 같은 응답은 파일 캐시를 사용할 수 있다.
- 실행 보고서: `data/raw/prewarm_report.json`. 목적지마다 갱신하며 다음 실행 시 보고서는 덮어쓴다. 중단 후 재실행해도 DB에 저장 완료된 데이터는 남는다.
- 키와 공급자 예외 본문은 보고서에 기록하지 않는다. 실패 시 예외 종류만 남긴다.

로컬에서 사전 수집해도 Git에 제외된 DB·캐시가 배포 서버로 자동 전달되지는 않는다. 배포 서버에서도 준비를 실행하고 `data/`가 지속되는 저장 공간을 사용해야 한다. 서버 재시작·재배포로 DB와 캐시를 지우면 긴 최초 수집이 다시 발생한다.

## 완료 판정

| 상태 | 의미 |
|---|---|
| `done` | 후보 동과 실거래가 있으며 수집 오류·통근 시간/요금 결측이 감지되지 않음 |
| `partial` | 일부 지역 수집 실패, 통근 시간/요금 미확인 또는 전체 실거래 없음 |
| `failed` | 목적지 검색 실패, 후보 동 없음 또는 수집 중 예외 |
| `interrupted` | 사용자가 실행 중단 |

종료 코드 0은 모든 대상 `done`, 1은 부분 실패·실패 포함, 2는 필수 키 미설정, 130은 사용자 중단이다. 보고서는 단계별 소요 로그 및 후보 동·실거래·통근 결측 수를 함께 확인하는 데 사용한다. `--status`의 통근 행 수만으로 데이터가 유효하거나 예산 조건이 충족된다고 판정하지 않는다.

일부 시군구가 실패하면 해당 지역을 건너뛰고 나머지를 준비하며, 다음 목적지도 계속 처리한다. 재실행은 완료된 시군구와 저장 통근을 재사용한다. 기존 수집기가 캐시한 `NO_RESULTS` 등의 경로 오류는 자동 삭제·재조회하지 않으므로 `partial`이 계속되면 원인을 확인해야 한다. 이 명령에는 강제 갱신·DB 삭제 기능이 없다.

## 성능과 한계

사전 수집은 사용자 대기 시간을 준비 단계로 옮기는 작업이다. 처음 수집하는 지역의 격자 탐색·시설 조회 알고리즘 자체를 단축하지 않는다. 기록상 2026-11-22 로컬 판교 첫 수집에서는 시군구 저장 완료 시각이 약 17:00~17:38에 걸쳐 있었고, 특히 넓은 시군구의 수집이 오래 걸렸다. 문서의 이전 약 4분 실측이 모든 환경에서 재현된다고 가정하지 않는다.

처음 보는 목적지는 지역·통근 API 호출과 사용량이 발생할 수 있다. 전체 대상 수집을 한꺼번에 시작하기 전에 목적지 하나로 소요 시간과 계정의 쿼터를 확인한다. 무료 한도와 가격은 기존 조사 문서의 수치 대신 현재 계정의 콘솔에서 확인한다. 자동 스케줄 실행, 전국 수집, 데이터 자동 갱신은 이번 범위에 포함하지 않는다.

## 연결 재사용과 측정

수집 공통 HTTP 클라이언트는 공급자별 최대 8개 연결 풀을 재사용한다. 기존 격자 간격・반경・주택 유형・기간・점수 계산은 변경하지 않는다. 같은 인증・URL・요청 파라미터・재시도 조건의 진행 중 요청만 공유하고, 완료 응답을 새로 메모리에 장기 저장하지 않는다. 파일 저장은 임시 파일을 교체하여 부분 쓰기를 읽지 않게 한다. 캐시 파일명의 기존 해시 규칙은 유지한다.

`http_metrics`는 공급자별 요청 수, 파일 캐시 적중/미적중, 실제 네트워크 시도, 재시도, HTTP/연결 오류, 네트워크 누적 초, 재시도 대기 초, 중복 대기 수/초를 집계한다. URL・쿼리・키・원문 응답은 포함하지 않는다. 수집 로그는 법정동 탐색, 대표 지점/시설, 실거래의 단계별 ms를 추가 기록한다. 병렬 요청의 누적 초는 전체 경과 시간과 같지 않으며 보고서 수치는 프로세스 누적값이다.

연결 재사용과 중복 요청 테스트는 가짜 HTTP 전송으로 검증했다. 실제 외부 API를 새로 호출한 수집 전후 벤치마크는 아직 수행하지 않았으므로, 40분이 얼마나 단축됐는지는 확정하지 않는다. 격자 탐색 스케줄러는 변경하지 않는다.

## 첫 검색의 시군구 병렬 처리

지역 준비 완료 문구에는 `전체 경과 N초`, Dataset 완료 문구에는 `데이터 준비 전체 경과 N초 (조건 해석·설명 제외)`를 포함한다. 화면의 단계 제목 시간이 개별 하위 작업의 첫 `ms`를 표시할 수 있으므로 전체 수집 시간은 완료 문구의 값을 확인한다. 이 변경은 측정 표시를 보완하며 수집 속도 자체를 개선하지 않는다.

완료되지 않은 시군구는 전용 실행 풀에서 프로세스 전체 최대 2곳까지 수집한다. 내부 동 수집 4개・조회 8개 풀과 분리하여 중첩 실행의 교착을 피한다. 공급자별 HTTP 연결 풀의 기존 최대 8개 제한은 유지한다. 이는 초당 요청 횟수 제한을 의미하지 않으며, 실제 공급자 사용량과 429 재시도는 배포 후 확인해야 한다. 여러 요청에서 동일한 시군구를 동시에 필요로 해도 기존 시군구 잠금 안에서 완료 상태를 다시 검사한다.

검색 반경・격자점・대표 지점・시설 종류・거래 기간・점수 계산・응답 캐시 저장 규칙은 변경하지 않는다. 완료 지역은 작업 큐에 넣지 않는다. 시군구 저장 순서가 바뀌어도 Dataset의 동은 코드순으로 구성한다. 통상적인 지역 실패는 기존처럼 해당 지역을 제외하고 계속하며, 예상하지 못한 작업 예외가 발생하면 나머지 제출 작업의 완료를 기다린 뒤 오류를 전달한다. 기존 카카오 자료의 저장·재사용 허용 범위 문제를 해결하는 변경은 아니다.

후보 지역 탐색, 전체 지역 준비, 통근, Dataset 구성에 `ms`를 기록하고 Dataset 완료 로그에는 데이터 계층 전체 `total_ms`도 기록한다. 전체 지역 준비 시간과 개별 지역 시간은 중첩되므로 합산하지 않는다. Gemini 조건 해석・설명 시간은 포함하지 않는다. URL・API 키・원문 응답을 측정값에 넣지 않는다.

`tests/test_collection_schedule.py`는 실제 외부 호출 없이 두 검색의 동시 실행 상한, 완료 지역 재사용, 실패 후 작업 정리, 저장 순서에 독립적인 Dataset·추천 결과를 확인한다. Render에서 확인한 기존 첫 검색 약 5분과 조건 변경 약 12초는 사용자 관찰값이다. 이번 수정 후 실제 최초 수집 시간・API 요청 수・최대 메모리는 아직 측정하지 않았고, 2배 빨라진다고 보장하지 않는다. 배포 후 비슷한 무캐시 상태에서 후보 수・완료 지역 수・각 단계 `ms`・429 여부를 함께 비교한다. 벤치마크를 위해 운영 DB를 임의로 삭제하지 않는다.
