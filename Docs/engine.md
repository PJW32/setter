# 추천 모델 (점수 엔진)

소개서 표현: **"LLM 기반 선호 추출 + 다기준 가중합(MCDA) 추천 모델"**. 학습하는 ML 모델이 아니다.

- 코드: `engine/` (외부 API·LLM 없음)
- 원칙
  - LLM 은 양 끝(발화 해석, 결과 설명)에만 쓰고 **점수 계산은 전부 코드**가 한다
  - **같은 입력이면 항상 같은 순위** (동점은 동 코드 순)
  - **지역 무관**: 코드에 시군구·목적지 이름이 없다. 들어온 동 데이터와 거래만 보고 계산한다

```
Dataset(동 목록 + 실거래) ─┐
Params(목적지, 주택 유형…) ─┼─ build_features ─→ 동별 요인 원값
                           │
State(단계, 필수 조건) ─────┴─ rank ─→ Result(순위, 기여도, 제외 이유, 아깝게 탈락)
                                         └─ compare(이전, 지금) ─→ 순위 변동 + 요인별 원인
```

## 1. 요인 5개

| key | 이름 | 방향 | 원값 | 단위 |
|---|---|---|---|---|
| `monthly_cost` | 월 총비용 | 낮을수록 좋음 | 월세 + 보증금 × 환산이율 ÷ 12 + 월 교통비. 조건에 맞는 실거래의 **중앙값** | 만원 |
| `commute` | 통근 시간 | 낮을수록 좋음 | 동 대표 지점 → 목적지역 대중교통 최단 경로 (+ 역에서 회사까지 도보) | 분 |
| `station_access` | 역 접근성 | 낮을수록 좋음 | 가장 가까운 지하철역까지 도보 (추정). 반경 3km 안에 역이 없으면 60분 | 분 |
| `convenience` | 생활 편의 | 높을수록 좋음 | 편의점·약국(500m)·대형마트(1.5km) 수를 항목마다 0~100 으로 바꾼 평균 | 점 |
| `quiet` | 조용함 | 낮을수록 좋음 | 반경 500m 주점 수 (상가정보 I211) | 개 |

- 월 교통비 = 편도 요금 × 2 × 월 근무일(22)
- 관리비는 실거래 데이터에 없음 → 화면에 "데이터 없음, 직접 확인"

## 2. 비교 기준 `Params` (모든 동에 똑같이 적용)

| 항목 | 기본값 | 근거 |
|---|---|---|
| `destination` | (대화에서 정함) | 목적지역 이름 = 통근 데이터 키 |
| `house_types` | 오피스텔, 단독다가구 | 33㎡ 이하 원룸 월세는 이 두 유형에서 나온다 (연립다세대는 거의 없음) |
| `max_area_m2` | 33 | 원룸 기준. 단독다가구는 계약면적, 나머지는 전용면적 |
| `new_contracts_only` | True | 갱신 계약은 시세보다 낮게 잡힘. 구분 없는 거래는 포함 |
| `conversion_rate` | 0.05 | 법정 전월세 전환율 = 기준금리 3.00% + 2%p (2026-11-20 기준, 마감 후 고정) |
| `work_days` | 22 | |
| `min_samples` | 5 | 실거래가 이보다 적으면 월 총비용 "데이터 부족" |

> 월세 0원(전세) 거래는 제외한다. 원룸 월세 비교가 목적이다.

## 3. 가중치: 숫자 대신 단계

LLM 은 0.37 같은 실수를 고르지 않고 단계를 고른다. 숫자 변환은 `engine/factors.py` 에서만 한다.

| 단계 | 값 |
|---|---|
| 매우 중요 | 4 |
| 중요 | 3 |
| 보통 | 2 (언급하지 않은 요인의 기본값) |
| 조금 | 1 |
| 상관없음 | 0 |

합이 1이 되도록 나눈다. 모두 "상관없음"이면 똑같이 나눈다.
예: 월 총비용 "매우 중요", 나머지 "보통" → 4/12 = 0.33, 나머지 각 0.17.

"필수" 단계는 없다. 한도가 있는 조건은 아래 **필수 조건**으로 따로 받는다 ("월세 60 넘으면 안 돼" = 필수, "싸면 좋겠어" = 선호).

## 4. 필수 조건 `Constraints`

| 조건 | 판정 |
|---|---|
| `max_deposit`, `max_monthly_rent` (예산) | 동의 실거래 중 예산 안 거래가 **3건 이상**이면 통과. 통과한 동의 월 총비용은 **예산 안 거래의 중앙값**으로 바꾼다 (실제로 이 사용자가 낼 금액) |
| `max_commute_min` | 통근 > 한도면 제외 |
| `max_monthly_cost` | 월 총비용 > 한도면 제외 |

- 실거래가 5건 미만인 동은 예산을 **확인할 수 없으므로 제외하지 않고** "예산 확인 불가" 표시
- 통근 데이터가 없는 동은 통근 한도로 제외하지 않고 "통근 한도 확인 불가" 표시
- 제외된 동마다 **얼마나 풀면 들어오는지**(`relax_to`)를 계산한다
  - 예산: 위반도가 작은 실제 거래 3건을 선택하고, 그 거래들이 함께 들어오도록 필요한 보증금·월세 한도만 올린다. 이미 충족한 한도는 완화 제안에서 제외한다. 서로 다른 거래의 값으로 가상의 조건 일치 거래를 만들지 않는다.
  - 통근·월 총비용: 그 동의 값
- 통과한 동이 3곳 미만이면 **가장 적게 풀면 되는 동 3곳**을 `near_misses` 로 함께 보여준다

## 5. 정규화 (고정 구간)

```
정규화 값 = clip((원값 − 하한) / (상한 − 하한), 0, 1)   낮을수록 좋은 요인은 1 − 값
하한·상한 = 필수 조건 적용 전 '전체 후보'의 5 백분위·95 백분위
```

- **필수 조건과 무관하게 구간을 정한다.** 예산을 바꿔 동 하나가 빠져도 다른 동의 정규화 값은 그대로다. 그래야 "왜 순위가 바뀌었는지" 설명할 수 있다 (테스트 `test_commute_limit_excludes_without_changing_others`)
- 5~95 백분위라 극단값 하나가 다른 동을 몰아붙이지 않는다
- 후보 집합(목적지 반경 안 동)이 바뀌면 구간도 바뀐다. 목적지가 같으면 고정

## 6. 데이터 부족

- 교통요금이 없으면 월 총비용은 `null`이다. 요금이 실제 0원인 도보 경로와 구분하며, 월 총비용 한도가 있으면 "월 총비용 한도 확인 불가" 플래그를 표시한다. 기존 미확인 후보 유지 정책에 따라 후보에 남을 수 있지만 한도 충족이 검증된 것은 아니다.
- 예산 필터로 선택한 거래가 있으면 월 총비용과 상세의 월세·보증금 중앙값·표본 수도 모두 같은 예산 안 거래를 기준으로 표시한다. 예산 비율 플래그의 분모는 전체 비교군 수를 유지한다.
- 보증금 상한 0원에는 실제 보증금 0원 거래만 해당한다. 양수 보증금으로 제외한 후보의 위반도와 완화 제안도 JSON에서 표현 가능한 유한한 값으로 반환한다.

- 값이 없는 요인은 **전체 후보 정규화 값의 중앙값**으로 채우고 `estimated` 와 "○○ 데이터 부족" 플래그를 단다
- 0점 처리(불리)나 요인 제외 후 재정규화(데이터 없는 쪽이 유리)를 하지 않는다 → 데이터가 없다는 이유로 이득도 손해도 보지 않는다

## 7. 점수와 기여도

```
기여도_k = 100 × w_k × 정규화 값_k
점수 = Σ 기여도_k     (0~100)
```

LLM 은 이 기여도로 "이 동의 가장 큰 강점"을 설명한다 (상위 2개 요인).

## 8. 순위 변동 분해 (`engine/diff.py`)

두 동 A, B 의 점수 차 = Σ 100 × w_k × (A의 정규화 값_k − B의 정규화 값_k)

이전과 지금의 이 항을 요인별로 빼면 **격차 변화가 요인별로 정확히 나뉜다** (합이 맞아떨어짐, 테스트로 확인).

예 (실데이터, 월 총비용을 "매우 중요"로): 단대동이 동원동을 추월
`격차 −1.42 → +2.02 = 월 총비용 +2.56, 통근 +1.15, 역 −0.57, 조용함 +0.57, 생활 편의 −0.28`

`compare(prev, cur)` 반환: `moves`(순위 변동), `overtakes`(현재 상위 3곳의 추월 분해), `weight_change`, `entered`, `dropped`.

## 9. 대화 상태 (`engine/state.py`)

서버가 들고 있는 것: 요인별 단계, 필수 조건, 비교 기준(Params), 변경 이력.
LLM 은 **변경분만** 낸다. `apply_changes` 가 검증하고, 알 수 없는 값은 버리고 이유를 남긴다.

```json
{
  "set_constraints":   {"max_monthly_rent": 60, "max_deposit": 1000, "max_commute_min": 50},
  "clear_constraints": ["max_monthly_cost"],
  "params":            {"destination": "판교역", "house_types": ["오피스텔"]},
  "preference_changes": [{"factor": "monthly_cost", "level": "매우 중요", "evidence": "월세가 제일 중요해"}]
}
```

검증 규칙
- 모르는 필수 조건·요인·단계·주택 유형은 버림 (`rejected` 에 이유)
- 값 범위 밖이면 버림 (보증금 0~10억, 월세 1~1000만, 통근 5~240분)
- 지원하지 않는 목적지는 버림
- 원래 상태는 바꾸지 않고 새 상태를 만든다 (가정 질문에 그대로 쓰기 위해)

## 11. 알려진 한계와 결정 대기

- **예산 안 거래가 아주 적은 동**: 신원동처럼 127건 중 3건(2%)만 예산 안이어도 통과하고, 그 3건으로 월 총비용을 계산해 싸 보인다. "예산 안 비율 10% 이상" 같은 하한을 둘지 결정 필요
- **유형 혼합**: 단독다가구(월세 중앙값 약 50만)와 오피스텔(약 83만)을 섞으면 오피스텔이 많은 동이 비싸 보인다. 기본은 둘 다 포함, 사용자가 유형을 고르면 바뀐다
- **면적 기준 차이**: 단독다가구 33㎡는 계약면적이라 오피스텔 전용 33㎡보다 실제로 작다
- 대표 지점 한 점 기준이라 넓은 동은 위치에 따라 실제와 차이가 크다
