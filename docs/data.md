# 데이터

- 추천 단위: **법정동** (월세 실거래가가 법정동 단위로만 나온다)
- 방식: 저장된 지역만 쓰지 않는다. **목적지가 정해지면 주변 지역을 확인하고, 없으면 그 자리에서 수집해 저장**한다
- 시연 안정성을 위해 주요 목적지 주변은 미리 수집해 둔다
- 상세 조사 기록: [data-sources.md](data-sources.md)

## 2. 실시간 지역 수집

```
목적지 이름 ─(카카오)→ 목적지역 ─(반경 10km, 2km 격자 좌표→법정동)→ 후보 시군구 목록
   └ 시군구마다: 저장돼 있으면 사용 / 없으면 수집 → SQLite 저장
        ├ 법정동 목록 (400m 전국 공통 격자를 시군구 안에서 넓혀 감)
        ├ 동마다 대표 지점, 가장 가까운 역, 편의시설 수, 주점 수
        └ 전월세 실거래 12개월 × 3유형
   └ 후보 동 = 후보 시군구의 동 중 목적지역 반경 10km 안
   └ 통근: (동, 목적지역) 쌍이 저장돼 있으면 사용 / 없으면 카카오 대중교통 호출 → 저장
```

### 2.1 목적지 해석 (`backend/regions.py: resolve_destination`)

1. "○○역"이면 지하철역 카테고리 검색
2. 동네 이름이면 주소 검색의 지역 결과 (예: "여의도" → 영등포구 여의도동)
3. 그 밖(회사·건물)은 키워드 검색
4. 결과를 **가장 가까운 지하철역**에 붙인다 → 통근 키 = 역 이름. 장소에서 역까지 도보 시간은 통근에 더한다
   - "판교 회사"와 "판교역"이 같은 통근 데이터를 같이 써서 대중교통 호출 한도를 아낀다

| 입력 | 결과 |
|---|---|
| 판교역 | 판교역 |
| 카카오 판교아지트 | 판교역 (+ 도보 2분) |
| 을지로 | 을지로입구역 (+ 도보 3분) |
| 여의도 | 여의나루역 (+ 도보 5분) |
| 역삼동 | 강남역 (+ 도보 9분) |
| 광화문 | 경복궁역 (+ 도보 5분) |

### 2.2 법정동 목록과 대표 지점 (`collectors/region.py`)

- **격자**: 위도 37.5° 기준 400m 간격의 전국 공통 격자. 어디서 시작해도 같은 격자점을 쓰므로 캐시가 재사용되고 결과가 재현된다
- **법정동 찾기**: 시군구 안의 한 점에서 격자를 넓혀 가며 좌표 → 법정동 변환, 법정동 코드 앞 5자리가 그 시군구인 점만 따라간다. 400m보다 작은 동은 빠질 수 있다
- **대표 지점 = 생활 중심**: 동 안 격자점마다 반경 300m 편의점 수를 세고, 그 수로 가중한 무게중심에 가장 가까운 격자점. 넓은 동에서 산·공원·업무지구 한가운데가 대표 지점이 되는 것을 막는다 (예: 삼평동 가장 가까운 역 야탑역 24분 → 판교역 13분). 편의점이 없으면 카카오 법정동 대표 좌표

### 2.3 실거래 정규화 (`collectors/molit.py`)

- 요청: `LAWD_CD`(시군구 5자리) × `DEAL_YMD`(월) × 유형 3개, 페이지 1000건
- 동 매칭: (시군구 코드, `umdNm`) → 법정동 코드
- 금액은 쉼표가 붙은 문자열(`"11,000"`) → 숫자(만원)
- 면적: 단독다가구 `totalFloorAr`(계약면적), 나머지 `excluUseAr`(전용면적)

## 3. 저장 형태

### 3.1 SQLite `data/store.sqlite` (실시간 수집 저장소, 깃 제외)

| 테이블 | 열 |
|---|---|
| `sgg` | code, sido, name, status(done/error), dong_count, deal_count, collected_at, error |
| `dong` | code, sgg_code, data(JSON: 아래 동 레코드) |
| `deal` | dong_code, sgg_code, house_type, area_m2, area_kind, deposit, monthly_rent, deal_ym, contract_kind |
| `commute` | dong_code, dest_key, data(JSON: min, fare, transfers, walk_min, mode, lines, map_url) |

### 3.2 동 레코드

```json
{
  "dong_code": "4113510300", "sido": "경기도", "sgg": "성남시 분당구", "name": "정자동",
  "lon": 127.11, "lat": 37.36, "point_source": "생활 중심 (...)", "area_km2_est": 5.44,
  "station": {"name": "정자역", "lines": ["신분당선", "수인분당선"], "dist_m": 260, "walk_min": 5, "lon": 127.10, "lat": 37.36},
  "convenience": {"편의점": 21, "약국": 9, "대형마트": 6},
  "bars": {"count": 31, "source": "상가정보 주점(I211)"}
}
```

통근은 목적지마다 달라서 동 레코드가 아니라 `commute` 테이블에 둔다. 엔진에 넘길 때 `commute: {목적지역: {...}}` 로 붙인다 (역에서 회사까지 도보 포함).

### 3.3 초기 수집본 (참고용)

`data/dongs.json`, `data/rent_deals.csv`: 판교 출퇴근권 8개 시군구(106개 동, 실거래 108,582건)를 처음 수집한 파일. `scripts/demo_rank.py` 가 이것으로 엔진을 돌린다. 백엔드는 SQLite 를 쓴다.

### 3.4 응답 캐시 `data/cache/` (깃 제외)

모든 외부 API 응답을 요청 파라미터 해시로 저장한다 (키는 저장 안 함). 같은 요청은 다시 부르지 않는다. 한도 초과 같은 일시 오류 응답은 저장하지 않는다.

## 4. 호출 한도와 규모

| API | 무료 한도 | 시군구 1개(동 약 15개) 처음 수집 | 비고 |
|---|---|---|---|
| 카카오 로컬 (좌표 변환·카테고리·키워드) | 각 일 10만 건 | 약 1,000~2,000건 | 넓은 시군구(용인 처인구 등)는 수천 건 |
| 카카오 대중교통 경로 | **일 1,000건** (초과 건당 10원) | 동 수만큼 × 목적지역 | **병목**. 새 목적지 하나에 후보 동 100~150개 |
| 국토부 실거래 | 개발계정 API별 일 1만 건(통상, 미확인) | 36건 | |
| 상가정보 | 미확인 | 동 수만큼 | |
| ODsay | 약 30건/일 (2026-11-20 실측) | 쓰지 않음 | 교차 확인용 |

처음 보는 목적지의 수집 시간은 환경과 후보 시군구에 따라 크게 달라진다. 초기에는 판교역 주변 13곳 약 4분으로 기록했으나, 2026-11-22 로컬에서는 약 40분이 소요됐다. 국토부 실거래는 `python scripts/prewarm_rent.py --saved-regions --offline`으로 기존 캐시에서 준비할 수 있다. 카카오 결과의 장기 저장・배포 범위는 별도 확인이 필요하며 전체 사전 수집은 기본 차단한다. 기존 저장 상태는 `python scripts/prewarm_data.py --status`로 확인한다. 상세 실행·완료 판정·배포 시 데이터 유지는 [사전 수집 운영](data-prewarm.md)을 따른다.

## 5. 한계 (화면·소개서에 표시)

- 실거래가는 **과거 계약**이지 현재 매물 가격이 아니다 → "시세 참고용"
- 통근 시간은 출발 시각을 지정할 수 없는 추정값 (카카오가 ODsay보다 길게 나온다: 정자역→판교역 16분 vs 8분, 대기 시간 포함으로 보임)
- 역 도보 시간은 직선거리 기반 추정
- 대표 지점은 동 안의 한 점. 넓은 동은 위치에 따라 실제와 다르다
- 실거래가 적은 동(외곽)은 월 총비용 "데이터 부족"
- 관리비·치안·채광·집 상태는 데이터 없음 → "확인 불가"로 분리
- 마감 후에는 수집 코드와 설정을 바꾸지 않는다. 실행 중 새 지역을 받아오는 것은 기능 동작이며, 소개서에 "실시간 공공데이터 수집 구조"로 명시한다
